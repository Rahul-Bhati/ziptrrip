## Overall stack decisions

| Layer | Choice | Why | Rejected alternatives |
|---|---|---|---|
| Language | TypeScript (frontend + backend) | Type safety; extra points in the assignment; one `Todo` shape shared everywhere | Plain JS: no compile-time checks |
| Backend | Express 5 | Most widely known Node framework; v5 forwards errors from `async` handlers to error middleware automatically | Fastify (less familiar), Next.js (mixes frontend/backend, hides backend work) |
| Validation | Zod | One schema gives both runtime validation and a TS type | Hand-written `if` checks: repetitive, easy to miss cases |
| Database | SQLite via `better-sqlite3` | Real SQL database stored in a single file: zero setup for reviewers | JSON file (no queries, unsafe concurrent writes), Postgres/Mongo (reviewer must run a DB server), Prisma (generated "magic" code) |
| Frontend | React + Vite **multi-page** build | Separate HTML entry per page means real full-page navigation = true MPA | Next.js / React Router: client-side routing behaves like an SPA |
| Tests | Vitest + Supertest | Native TS/ESM support; Supertest hits the app without opening a port | Jest (extra TS/ESM config) |

## Step 1: Server project setup

**Goal:** a TypeScript + Express server that compiles, runs, and answers one request, so later steps start on a solid base.

### Files

#### `.gitignore`
Keeps generated or private files out of git:
- `node_modules/`: recreated from `package-lock.json` by `npm install`; huge and machine-specific.
- `dist/`: compiled output; regenerated by `npm run build`. Committing it would mean two copies of the same code that can drift apart.
- `*.db` (+ `-journal`, `-wal`, `-shm`): SQLite data is runtime state, not source code.
- `.env`, editor and OS files: personal / secret, not project files.

#### `server/package.json`
- **`"type": "module"`**: use standard ES Modules (`import`/`export`) instead of legacy CommonJS (`require`). ESM is the JavaScript standard and what modern tools (Vitest) are built around.
- **Scripts:**

  | Script | Command | Purpose |
  |---|---|---|
  | `dev` | `tsx watch src/index.ts` | Run TS directly, restart on file save (development) |
  | `build` | `tsc -p tsconfig.build.json` | Compile TS → JS into `dist/` (Node cannot run `.ts`) |
  | `start` | `node dist/index.js` | Run compiled output (production) |
  | `typecheck` | `tsc --noEmit` | Report type errors only. **Needed because `tsx` and Vitest strip types without checking them.** |
  | `test` | `vitest run` | Run all tests once |

- **Runtime dependencies** (needed when the server runs):
  - `express` (v5): web framework. In Express 4 an error thrown inside an `async` handler was *not* caught, so the request hung. Express 5 forwards it to the error middleware automatically.
  - `better-sqlite3`: SQLite driver. **Synchronous** API: SQLite runs inside the Node process (no network round-trip), so queries take microseconds; sync code is simpler and faster here.
  - `zod`: request validation (used in step 3).
- **Dev dependencies** (only needed while developing/testing): `typescript`, `tsx`, `vitest`, `supertest`, and `@types/*` (type definitions for libraries written in JS).
- **`@types/node` pinned to v22** to match the Node version we actually run. Newer types could let us call APIs that don't exist at runtime.
- **Deliberately not added:** `nodemon` (`tsx watch` does it), `ts-node` (slower, awkward with ESM), `cors` (Vite dev proxy makes it unnecessary, see step 6), `dotenv` (only one setting, `PORT`).
- **TypeScript 7** was installed (the new Go-based native compiler). Same language rules, much faster compiles.

#### `server/tsconfig.json`
Type-checking rules for the editor and `npm run typecheck`. Covers `src/` **and** `tests/`, emits nothing (`noEmit`).
- `strict: true`: all safety checks on; most importantly, `null`/`undefined` must be handled explicitly.
- `noUncheckedIndexedAccess: true`: `rows[0]` is typed `Todo | undefined`, forcing a "not found" check. Directly prevents a common bug in `getById`.
- `noImplicitReturns`, `noFallthroughCasesInSwitch`: catch forgotten `return`s and `break`s.
- `module` / `moduleResolution: NodeNext`: follow Node's real ESM rules. **Consequence:** relative imports end in `.js` (e.g. `import { createApp } from "./app.js"`) even though the source file is `app.ts`, because TS does not rewrite import paths and after compiling the file *is* `app.js`.
- `target: ES2022`: Node 22 runs modern JS natively; no need to downlevel.
- `types: ["node"]`: only load Node's global types, not every `@types` package.

#### `server/tsconfig.build.json`
Extends `tsconfig.json`, but compiles **only `src/`** into `dist/` with source maps.
**Why a second file:** with one config, either tests would get compiled into the production `dist/`, or tests would not be type-checked at all. Splitting gives both: tests are type-checked, but never shipped.

#### `server/src/app.ts`
Exports `createApp()`, which **builds** the Express app but does **not** start it.
- `express.json()`: middleware that parses JSON request bodies into `req.body` (otherwise `undefined` on POST/PATCH).
- `GET /api/health` → `{ "status": "ok" }`: standard liveness check (used by load balancers / Docker); also proves the setup works.
- All routes are under `/api` so the frontend dev server can forward exactly those paths to the backend (step 6).

#### `server/src/index.ts`
The only file that calls `.listen(PORT)`. Reads `PORT` from the environment, defaulting to `3000`.

### Key design decision: `app.ts` (build) vs `index.ts` (start)
Splitting them lets tests import `createApp()` and send requests through Supertest **without opening a real port**: no "port already in use" errors, no server left running after tests.
In later steps `createApp()` will **receive the database as a parameter** (*dependency injection*): tests pass an in-memory database, the real server passes a file database.

### Verification
- `npm run typecheck`: passes
- `npm run build`: produces `dist/app.js`, `dist/index.js`
- `GET /api/health` → `200 {"status":"ok"}`
- `better-sqlite3` native module loads on Windows / Node 22 (SQLite 3.53)
